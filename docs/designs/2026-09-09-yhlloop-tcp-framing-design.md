# YhLoop TCP 原生帧接入设计

日期：2026-09-09  
范围：中控 MES 的 ShineLab/YhLoop 被动 TCP 监听与离线验证  
状态：设计已确认，待实现

## 1. 背景与证据

当前现场拓扑是控制电脑作为 TCP Client，中控电脑作为 TCP Server，目标为
`192.168.10.11:5500`。TCP 三次握手能够建立，但现有服务使用
`StreamReader.ReadLineAsync()`，约 10 秒无应用层消息后连接被关闭。

对 `res/ShineLab/ShPipeClient.dll`、`ShPipe.dll` 和
`ShDeviceFamily.dll` 的静态分析已经直接证明：ShineLab 的 TCP 层不是 LF/CRLF
分帧，而是以下二进制帧：

```text
55 AA | length_hi length_lo | UTF-8 JSON | 00
```

其中 `length` 为 JSON 字节数加 1（结尾 NUL），按大端序写入；完整帧总长度为
`length + 4`。接收端先去掉 4 字节帧头和结尾 NUL，再把 JSON 交给 YhLoop
解码器。

`BindModule` 是此前 IRAY-C 路径中发现的符号/方法名，不能据此推断当前
YhLoop 的首帧或业务字段。YhLoop 首帧的具体方法名和业务 body 仍以现场真实
报文或厂商示例为准；本设计不主动猜测或发送它。

## 2. 目标与非目标

### 目标

1. 让 MES 监听器按 ShineLab 原生 55AA 长度帧接收和发送。
2. 正确处理 TCP 半包、粘包、前导噪声、无效长度和断线重连。
3. 收到合法认证消息后，仅回复同一 `strID`/`strMethod` 的认证结果。
4. 保留现有状态、任务事件和响应关联逻辑，不改变串口或仪器控制层。
5. 通过完全离线的 fixture、单元测试和本机回放证明协议行为。
6. 记录可审计的原始帧摘要，但不把完整敏感 body 写入普通日志。

### 非目标

- 不发送 `Config`、`Command`、泵控制、进样、停止、方法下载或任何猜测性
  YhLoop/IRAY 报文。
- 不把下游协议表中的换行 JSON 当作现场主协议。
- 不在没有真实报文证据时把 `BindModule` 应用于 YhLoop。
- 不修改设备串口、USB 或现场网线配置。

## 3. 方案比较

### 方案 A（采用）：原生帧解析器，旧换行格式仅作测试 fixture

在共享协议层增加 55AA 编解码和有界增量解析器，MES Server 与离线工具共用。
生产路径只接受原生帧；旧换行样例只用于证明“不应被误识别”的测试。

优点是与 DLL 证据一致、边界明确、现场行为可预测，且不会把两种协议的
自动探测误判带入生产。代价是旧的换行客户端必须升级或隔离。

### 方案 B：生产环境自动识别 55AA 与换行 JSON

收到连接后根据首字节在两种解析器之间切换。

优点是短期兼容性较高；缺点是前导字节、截断 JSON 和恶意输入可能造成错误
分流，且会掩盖现场配置错误。当前不采用。

### 方案 C：单独部署协议转换代理

MES 保持换行协议，代理负责 55AA 转换。

优点是可以暂不触碰现有业务代码；缺点是增加进程、端口、日志和故障点，
不符合当前先做本机离线验证的最小范围。当前不采用。

## 4. 推荐架构

### 4.1 共享帧编解码

在无网络依赖的共享协议层提供：

- `Encode(JsonElement/message)`：UTF-8 序列化、写入 55AA、大端长度和结尾 NUL；
- `TryReadFrame(...)`：从增量 byte buffer 中提取完整帧；
- `DecodePayload(...)`：严格 UTF-8、去除唯一结尾 NUL、返回 JSON 文本；
- 固定最大 payload/frame 长度（不超过 16 位长度字段，默认 64 KiB）；
- 明确的 `NeedMoreData`、`FrameReady`、`InvalidFrame` 结果，不抛出可恢复的
  半包异常。

MES Server 和 dispatcher 使用同一实现，避免一边修复而另一边继续发送 LF。

### 4.2 MES Server 读取循环

每个连接维护独立的 byte buffer：

1. `NetworkStream.ReadAsync` 读入原始字节；
2. 解析器扫描 `55 AA`，丢弃此前的噪声并保留可能的半个头；
3. 读取大端长度，长度越界则记录协议错误并关闭当前连接；
4. 完整帧到达后去掉 NUL，严格解析 JSON；
5. 对每个帧按现有 `statusHub`、任务服务和响应关联流程处理；
6. 同一读取批次中的多个帧逐个处理；未完成帧留在 buffer 等下一次读取。

空闲超时仍为配置项，默认 10 秒；收到任何完整合法帧后重置。停止服务或
连接替换时取消读取并完成挂起请求。

### 4.3 写入与认证

连接管理器不再持有 `StreamWriter`，改为持有当前 `NetworkStream` 和串行写
闸门；所有主动写入都通过共享帧编码器。

生产默认不主动探测。收到 `Certification` 且字段合法时，回复：

```json
{
  "strID": "<原 strID>",
  "strMethod": "Certification",
  "equipmentCode": "<原 equipmentCode>",
  "body": { "result": "Success", "msg": "" }
}
```

该 JSON 必须封装成同样的 55AA 帧。未知方法、缺少必填字段或 JSON 错误只记
录并继续/关闭（按错误类型决定），不自动生成业务响应。现有
`SendCertificationOnConnect` 若保留，仅作为明确的本地诊断开关，且也必须
使用原生帧；默认关闭。

### 4.4 日志与安全边界

每个接受、发送和丢弃事件记录：连接 ID、远端地址、帧长度、方法（若可解析）、
`strID` 摘要和 payload 哈希/前缀。默认不记录完整 body；长度超过上限或连续
无效帧达到阈值时主动关闭连接，防止无界内存增长。

## 5. 兼容与迁移

- `ShineLabTcpServer` 的现场主路径只使用 55AA。
- 旧 dispatcher 中的 LF 编解码要么切换到共享 55AA 编解码，要么显式标记为
  离线 legacy，不得继续作为现场入口。
- 现有业务 JSON 字段（`strID`、`strMethod`、`equipmentCode`、`body`）和
  状态 hub 语义保持不变。
- 文档中来自下游协议表的“换行 JSON”保留为历史参考，并明确与 DLL 原生
  framing 的差异，避免联调时按错误分帧排查。

## 6. 离线验证矩阵

1. 编码长度：ASCII、中文和空 body 均满足 `length = jsonBytes + 1`。
2. 解码完整帧：无换行也能解析认证和状态消息。
3. 半包：头、长度、JSON、NUL 分别跨多次 `ReadAsync` 仍只产出一帧。
4. 粘包：一次写入两到三帧，按顺序全部产出。
5. 噪声/坏帧：前导垃圾、长度为零、长度超限、缺少 NUL 不会污染下一帧。
6. 认证闭环：客户端帧触发一帧格式正确的 Success 响应。
7. 状态上报：Device/TaskFinish 等消息更新现有 hub，不触发串口访问。
8. 命令关联：仅在测试模拟器明确发起时验证响应关联；生产代码不自动发命令。
9. 空闲超时：认证后无后续帧按配置断开，并清理连接状态。
10. 旧换行输入：不会被误当成现场合法帧，测试结果明确记录。

## 7. 现场联调前置条件

离线测试全绿后，才允许把控制电脑目标设为 `192.168.10.11:5500` 并观察
真实首帧。首次现场联调只做：连接、被动接收、记录原始摘要、认证响应；不
点击自动进样、不发送 Config/Command，不修改仪器方法。只有拿到真实首帧和
厂商确认的响应字段后，才另行设计业务下发阶段。
