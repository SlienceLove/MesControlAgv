# WPF 界面展示优化推进方案

> 分支：`feature/wpf-ui-layout-optimization`
> 基线：2026-09-04
> 范围：只优化 WPF 信息架构、布局和可读性，不改变 MES、Adapter、设备协议或实体设备安全边界。

## 1. 结论先行

当前系统的服务边界基本清晰，WPF 通过 MES HTTP 契约访问业务，MES 负责任务/流程/审计，Adapter 负责设备协议和安全策略，Simulator 用于离线验证。当前最需要优化的是表现层的“信息架构”和“有限空间布局”，不是先重写后端。

目前主窗口把 15 个可见页面（另含 1 个隐藏兼容页）全部作为同一层 TabItem 放入一个导航栏；多个页面又把列表、详情、操作、日志同时铺开。窗口缩小时，固定宽度列和右侧面板会互相挤压，长文本只能依赖横向滚动，操作员看不到完整上下文。

本分支第一轮已经完成：

- 主窗口改为四组可折叠导航：运营总览、任务与设备、实验工作流、系统与诊断。
- 保留 `MainTabs`、`TabItem`、自动化 ID 和原有页面 DataContext，降低迁移风险。
- 将 TabControl 改为“只承载内容”，导航从内容区域独立出来，页面不再与一长串菜单争夺高度。
- 导航项使用单选状态、分组标题和滚动容器；窄窗口仍可以访问全部入口。
- 不改变任何任务派发、AGV 控制、AUBO 或仪器 I/O 行为。

## 2. 当前架构评估

### 2.1 可以保留的边界

| 层 | 当前职责 | 评价 |
| --- | --- | --- |
| `Contracts` / `Domain` | API DTO、任务/地图/流程领域模型 | 作为共享契约和领域核心，方向正确 |
| `Mes` | SQLite、任务状态机、流程版本、运行恢复、审计和排程 | 业务权威位置清晰，应继续保持 |
| `Adapter` | AGV、AUBO、工作站和设备协议转换，控制权和安全门禁 | 与 WPF 解耦，适合继续扩展设备 |
| `InstrumentGateway` | 仪器只读/受控写边界 | 读写分离和默认拒绝策略应保持 |
| `Simulator` | 可重复的离线运行和验收环境 | 应继续作为 UI 和流程回归的默认环境 |
| `Wpf` | MVVM 页面、操作员反馈和 HTTP 客户端 | 目前主要问题是 Shell/导航和布局耦合 |

### 2.2 需要演进的地方

1. **主窗口是手工聚合器。** `MainViewModel` 同时创建多个页面 ViewModel、刷新周期和操作命令；`ControlCenterModuleRegistry` 只覆盖部分核心模块，而 `MainWindow.xaml` 还硬编码了 ShineLab、AUBO、流程、诊断等页面。模块注册和实际导航存在漂移。
2. **所有页面一次性实例化。** 页面虽然有生命周期测试，但主窗口启动时仍会创建全部视图和较重的绑定树。后续应采用导航项元数据 + 视图工厂，按首次访问延迟创建。
3. **页面 DataContext 不统一。** 有的页面继承 `MainViewModel`，有的显式绑定子 ViewModel，有的依赖 `x:Name` 访问控件。这会增加页面复用和导航重构成本。
4. **领域模型和展示模型边界偏薄。** WPF 项目直接引用 `Domain`，`MainViewModel` 里有较多 API/状态拼接逻辑。后续可把页面需要的查询投影收敛到 Application/Contracts，避免 UI 了解过多领域细节。
5. **轮询范围偏大。** 当前刷新逻辑会在一个控制中心周期里更新任务、车队、KPI、设备状态、AUBO 和就绪信息。页面不可见时仍有刷新成本；应按模块可见性和刷新优先级分层。
6. **布局使用固定像素较多。** 多个 DataGrid 的列宽总和明显大于小窗口可用宽度，右侧详情/操作面板也采用固定宽度；这正是“显示不全”的主要技术原因。

## 3. WPF 具体问题与对应策略

| 问题 | 现象 | 策略 |
| --- | --- | --- |
| 一级入口过多 | 左侧菜单长、低频页面占据同一层级 | 分组折叠导航；高频入口放在“运营总览” |
| 列表列过多 | AGV/任务/设备表格需要横向滚动，重要列被推到屏幕外 | 核心列优先、次要列按窗口宽度隐藏/移入详情抽屉 |
| 列表和详情同时铺开 | 任务、AGV、设备页右侧面板挤压主列表 | 默认“列表 + 详情”两态；详情可折叠或在窄屏改为下方区域 |
| 工具栏过长 | 文件、刷新、提交、清空等按钮换行后挤占标题区 | 高频操作保留文字，低频操作收入“更多”菜单；使用 `WrapPanel`/命令分组 |
| 长文本撑高布局 | 错误、审计、路径文本导致页面跳动 | 固定详情区高度 + 内部滚动；摘要与完整内容分层显示 |
| 嵌套滚动容器 | 外层和内层都滚动，操作员难以判断滚动位置 | 每个页面只保留一个主滚动方向，表格自身负责行滚动 |
| 状态只靠颜色 | 在线、未知、失败在不同页面语义不一致 | 统一“颜色 + 文字 + 状态徽标”，`Unknown` 单独高亮并禁止盲目重试 |
| 所有模块同时刷新 | 切换页面时存在不必要请求 | 引入页面激活/停用生命周期和刷新策略，保留手工刷新入口 |

## 4. 分阶段推进

### 阶段 A：导航和外壳（本分支已开始）

- 完成分组导航和内容区解耦。
- 保留现有页面和自动化测试契约，避免一次性迁移所有 ViewModel。
- 增加主窗口窄屏、导航选择和页面切换回归测试。
- 目标：`820x480` 可访问全部入口，`1440x900` 下导航和内容稳定可扫描。

### 阶段 B：高频页面响应式布局（第一批完成）

优先顺序：任务监控 → AGV 通讯与调度 → 设备状态查询 → 样品/批量导入。

- 将表格列分成“核心列 / 次要列 / 诊断列”。
- 核心列使用 `*` 和最小宽度，次要列在窄窗口进入详情面板；诊断列默认隐藏但可恢复。
- 任务/AGV 页面采用 `GridSplitter` 或“详情抽屉”，窄窗口切换为上下布局。
- 统一空状态、加载中、过期、错误和重试提示。
- 验收：不依赖横向滚动即可完成最常见的查看、选择和操作。

### 阶段 C：工作流和排程页面

- 流程编辑器保持“左工具箱 / 中画布 / 右属性 / 底部校验”的结构，面板可折叠。
- 排程页把任务池、资源时间轴、阻塞原因和审计拆为可调整区域，避免固定 1140 像素时间轴强行撑宽窗口。
- 运行监控默认展示当前节点和异常，节点执行/设备操作/时间线作为可切换详情。

### 阶段 D：导航元数据和延迟加载

- 扩展 `ControlCenterModuleDescriptor`：分组、图标、默认入口、所需权限、刷新策略。
- 引入 `INavigationService`/视图工厂，页面首次访问时创建，离开时按策略暂停刷新。
- 让 `MainWindow` 只负责 Shell，页面和 ViewModel 由模块注册提供。
- 迁移完成后删除重复的硬编码 TabItem 映射，但保留自动化 ID 兼容层。

### 阶段 E：一致性和可观测性

- 建立统一主题资源：间距、字号、状态色、表格行高和详情卡片。
- 为关键页面记录布局版本和用户列布局；旧布局无法匹配时安全回退默认列。
- 使用模拟器生成固定任务/设备数据，做 820、1024、1280、1440 四档 UI 冒烟截图和人工验收。

## 6. 建议的后续最小切片

本轮已经处理了任务、AGV、设备、样品导入、批量导入和 ShineLab 页面，并完成实验方案、任务排程、流程运行监控的首轮比例适配；下一次提交继续做统一样式和细节抽屉：

1. 抽取统一的页面标题栏和状态徽标样式。
2. 将错误、路径、连接来源等长字段统一放进可展开的详情抽屉。
3. 为关键页面补充 `1024x640`、`1440x900` 两档截图/人工验收。

这样每个切片都能独立回归、截图和回滚，不会把 UI 改造与设备联调混在同一个提交中。
