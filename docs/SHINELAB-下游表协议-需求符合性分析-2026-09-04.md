# ShineLab 下游表协议需求符合性分析报告

**分析日期：** 2026-09-04<br>
**分析对象：** `下游表协议 - 序列进样.docx`<br>
**适用设备：** ShineLab、SHA-18i/AS18、CIC-D160+ 离子色谱相关软件和仪器<br>
**报告状态：** 协议草案评审版

## 1. 结论摘要

### 1.1 总体结论

按 2026-09-01 已确定的最新方案，本协议的总体架构方向基本符合，但接口字段、任务闭环和生产可靠性要求明显不足。

结论如下：

| 评审范围 | 结论 |
|---|---|
| ShineLab 作为 TCP Client、中控作为 TCP Server | 基本符合 |
| 中控不直接打开 SHA-18i/D160+ 串口 | 符合 |
| TCP 连接、换行分帧、基本认证 | 方向符合，细节缺失 |
| 单样品配置和启动 | 具备接口雏形，字段和动作映射不足 |
| 序列进样 | 不足，无法确认批量顺序和逐样品闭环 |
| 状态、报警、任务异常 | 不足 |
| 检测结果和结果文件归档 | 不足 |
| 断线恢复、幂等、补偿和生产安全 | 缺失 |
| 是否可以作为最终生产协议 | 不可以 |

### 1.2 建议决策

该文件可以作为“接口骨架/第一轮联调草案”继续推进，但不能直接签字定版，也不能据此进入真机自动运行或生产验收。

建议要求 ShineLab 技术团队基于本报告补充一版正式协议，完成字段、状态、错误码、动作映射和真机联调证据后，再进入单样品闭环验收。

## 2. 评审依据和架构基线

本次对照的上一版需求文件为：

- `docs/SHINELAB-SHA18I-INTERFACE-REQUIREMENTS-2026-09-01.md`
- 微信缓存目录中的 `中控--Shinelab.docx`
- `docs/ION-CHROMATOGRAPHY-INTERFACE-MEETING-REPORT-2026-09-01.md`

当前采用的目标链路为：

```text
ShineLab（TCP Client，负责串口和仪器动作）
        │
        │ TCP + JSON + LF
        ▼
中控/MES（TCP Server、任务、状态、审计、恢复）
        │
        │ HTTP 业务接口
        ▼
WPF 中控界面
```

ShineLab 负责：

- SHA-18i、D160+ 串口和设备状态机；
- 样品位置、通道、方法参数到设备协议的转换；
- 实际进样、检测、清洗、停止和异常处理；
- 设备状态、样品完成、任务完成、异常和检测结果上报。

中控负责：

- 创建任务并生成全局唯一 `task_uuid`；
- 下发样品、位置、通道、方法和启动/停止命令；
- 接收状态、完成、异常和结果；
- 保存任务、事件和接口日志；
- 在断线、超时和重启后进行状态恢复和人工处理。

历史的“中控直接占用串口控制 D160+/SHA-18i”方案已经停止采用，详见 `docs/ION-CHROMATOGRAPHY-DIRECT-CONTROL-IMPLEMENTATION-PLAN.md` 的说明。本协议只能评估 ShineLab 代理控制路线，不能替代底层串口/Modbus 协议。

## 3. 协议已覆盖内容

协议目前具备以下基础元素：

1. TCP 通讯；
2. 下游设备作为 Client、平台/主控作为 Server；
3. JSON 报文，以换行符处理粘包和半包；
4. 连接建立和重连后发送 `Certification`；
5. 通用字段 `strID`、`strMethod`、`equipmentCode`、`body`；
6. `Certification`、`UpdateInfo`、`AlarmInfo`、`Config`、`Command`；
7. `SampleFinish`、`TaskFinish`、`TaskError`、`Result`；
8. `Command` 中初步定义了启动、停止、检测、清洗等 action；
9. `sampleData` 可以承载多个样品行。

这些内容说明协议的总体思路与我们的中控架构兼容，但仍属于“报文示例级别”，尚未达到可直接实施的正式协议标准。

## 4. 逐接口符合性对照

| 接口 | 协议当前内容 | 对上一版需求的符合情况 | 主要缺口 |
|---|---|---|---|
| TCP 连接 | Client/Server、长连接、10 秒无消息判定、Client 重连 | 基本符合 | IP、端口、超时、退避、连接冲突处理未正式固定 |
| `Certification` | 每次建立连接发送，body 为空 | 部分符合 | SHA-18i 设备编码、版本、认证字段、失败码、认证安全机制缺失 |
| `UpdateInfo` | 1 秒上报，status 0/1/2，values 测点数组 | 部分符合 | 缺 task、sample、channel、position、stage、progress、errorCode |
| `AlarmInfo` | 只上报 errorMsg | 不符合 | 缺 task_uuid、样品、通道、报警码、时间、严重性、停止要求和处理建议 |
| `Config` | sampleData 包含 sampleID、sampleName、type、position、mPos、Channel | 不足 | 缺 task_uuid、进样方法、处理方法、检测方式、进样体积、单位、稀释参数、枚举定义 |
| `Command` | action 0～7，含取样、停止、检测、清洗等 | 部分符合 | 未给出 SHA-18i 实际映射、准备/查询/暂停/恢复/急停语义和幂等规则 |
| `SampleFinish` | task_uuid、finishDate | 不足 | 缺 sampleID、位置、通道、成功/失败、失败原因、是否继续 |
| `TaskFinish` | task_uuid、finishDate | 不足 | 缺开始/结束时间、总数、成功数、失败数、最终状态、结果文件信息 |
| `TaskError` | task_uuid、finishDate | 不符合 | 缺 errorCode、errorMsg、recoverable、requiresOperator、lastKnownStage |
| `Result` | task_uuid、testDate、sampleName、testItem、value、unit | 部分符合 | 缺 sampleID、方法、结果状态、质量标识、异常值语义、结果文件和校验值 |

## 5. 关键不符合和缺失项

### 5.1 报文示例不能直接作为实现依据

协议中的 JSON 示例存在以下问题：

- 使用中文弯引号，非标准 JSON 引号；
- JSON 中混入 `//` 注释；
- 个别字段缺少逗号；
- 部分括号层级不匹配；
- `Channel`、`channel`、`sampleID`、`sampleId` 等命名不统一；
- 请求、响应的外层和 `body` 层级描述不一致。

必须提供经过 JSON 校验器验证的完整示例，并给出 JSON Schema 或字段表。

### 5.2 响应结构存在冲突

通用响应表看起来把 `result`、`msg` 定义为响应字段，但具体 Config/Command 示例又将它们放在 `body` 内。

建议统一为：

```json
{
  "strID": "唯一请求号",
  "strMethod": "Command",
  "equipmentCode": "SHA18I",
  "body": {
    "task_uuid": "中控任务号",
    "action": 0,
    "result": "Success",
    "errorCode": "",
    "msg": ""
  }
}
```

`strID` 必须原样返回，`task_uuid` 必须原样透传。若厂家坚持将 `result/msg` 放在外层，需要同步修改中控解析规则并重新定义所有报文。

### 5.3 设备身份和适用范围不清楚

协议示例中的设备编码主要是 `Ge`、`B`、`IC_A`、`IC_C` 等，没有确认 SHA-18i 的正式 `equipmentCode`。

需要明确：

- 当前设备是 `SHA18I`、`AS18`、`SHA-18iA` 还是其他编码；
- ShineLab 是把 SHA-18i 和 D160+ 作为一个组合设备，还是分别上报；
- 一个 TCP 连接是否允许多个 `equipmentCode`；
- 该协议是否确实由当前 ShineLab 版本实现，而不是其他仪表通用协议。

### 5.4 `UpdateInfo` 不能满足状态看板

协议只定义了：

```text
status = 0 空闲
status = 1 运行中
status = 2 异常
values = 测点和阀状态数组
```

但中控当前需求需要显示：

```text
在线/离线、任务号、样品编号、样品名称、通道、位置、阶段、进度、报警
```

应至少补充：

```json
{
  "task_uuid": "task-001",
  "sampleID": "S-01",
  "sampleName": "标准样",
  "channel": "A",
  "position": 11,
  "stage": "Idle|Preparing|Injecting|Detecting|Washing|Completed|Error",
  "progress": 35,
  "errorCode": "",
  "errorMsg": ""
}
```

同时需要定义 `values` 中每个测点的名称、数据类型、单位、有效范围和告警含义。不能只写“共 9 个测点”。

### 5.5 Config 字段不足以表达序列任务

协议的 `sampleData` 只有少量基础字段，无法完整承载当前序列进样需求。

至少需要补充：

| 字段 | 说明 |
|---|---|
| `task_uuid` | 整批任务唯一编号 |
| `sampleID` | 中控样品唯一编号 |
| `sampleName` | 样品名称 |
| `type` | 样品类型和枚举表 |
| `sampleLevel` | 样品等级，如适用 |
| `position` | 样品瓶物理位置 |
| `mPos` | 机械盘位/位置，需明确与 position 的区别 |
| `channel` | A/B 或厂家实际通道定义 |
| `instrumentMethod` | 进样方法 |
| `processingMethod` | 结果处理/积分方法 |
| `detectionMethod` | 检测方式 |
| `volume`、`volumeUnit` | 进样体积和单位 |
| `cycleCount` | 循环/重复次数 |
| `dilution` | 稀释参数，无则明确为 null |
| `sequenceNo` | 序列顺序，不能依赖数组顺序而不说明 |

当前已验证的 ShineLab CSV 序列模型还涉及样品等级、处理方法、清除校正、循环次数、进样体积、进样单位、空白和色谱方法。TCP 协议需要明确这些字段是否支持，以及与 `instrumentMethod`、`processingMethod`、`detectionMethod` 的对应关系。

### 5.6 Command 动作映射不足

协议定义了 action 0～7，但描述主要是通用仪表或锗表语义，例如：

```text
0 启动取样
1 停止取样
2 启动检测
3 T1 自动
4 T3 自动
5 磨损检测
6 去污
7 清洗
```

这不能直接证明对应 SHA-18i 的真实动作。厂家必须提供动作映射表，包括：

- action 的整数值和名称；
- 目标设备和目标通道；
- 执行前置条件；
- 设备忙时返回值；
- 是否幂等；
- 正常停止和硬件急停的区别；
- 清洗、去污、初始化是否会改变任务状态；
- 启动命令收到响应后是“已接收”还是“已开始”；
- 发生通信中断时如何查询实际执行结果。

建议正式接口至少提供 `Prepare`、`StartInjection`、`StartDetection`、`Stop`、`Wash`、`QueryStatus` 的明确语义。暂停、恢复、取消可作为后续版本，但正常停止和急停边界必须在第一版明确。

### 5.7 完成和异常事件不支持完整任务闭环

当前 SampleFinish、TaskFinish、TaskError 的 body 过于简单。

单样品完成至少需要：

```text
task_uuid、sampleID、sampleName、channel、position、finishDate、
result、errorCode、msg、continueNext
```

整批完成至少需要：

```text
task_uuid、startDate、finishDate、totalCount、successCount、
failedCount、finalStatus、resultAvailable、errorCode、msg
```

任务异常至少需要：

```text
task_uuid、sampleID、stage、errorCode、errorMsg、occurredAt、
recoverable、requiresOperator、stopRequired
```

`AlarmInfo` 与 `TaskError` 也必须明确区分：

- `AlarmInfo`：设备实时报警，可以恢复，不一定导致任务失败；
- `TaskError`：导致任务失败、暂停或需要人工处理的任务级异常。

### 5.8 Result 不足以完成结果归档

当前 Result 只包含检测项、数值和单位。正式接口还需要：

- `sampleID`；
- `instrumentMethod`；
- `processingMethod`；
- `detectionMethod`；
- 结果成功/失败状态；
- 质量状态或异常标识；
- 空值、低于检出限、超量程、计算失败的表示方式；
- 结果文件名、共享目录相对路径；
- 文件 SHA256；
- 文件保留时间；
- 数据时间、时区和小数精度规则。

### 5.9 可靠性和安全语义缺失

协议还没有正式定义：

- 协议版本和字段版本；
- 能力查询；
- Certification 的认证内容和认证失败行为；
- IP、端口、连接超时和重连退避；
- 重复 `task_uuid` 的处理；
- 重复 Command 是否会重复进样；
- Config/Command 超时后的实际结果查询；
- 结果上报丢失后的补取；
- 事件是否需要 ACK；
- 消息顺序和重复消息处理；
- 设备忙时的拒绝码；
- TCP 连接被替换后的旧连接失效规则；
- 是否需要共享密钥、TLS、IP 白名单或网络隔离。

## 6. 当前项目已经具备的能力

仓库中控侧已经有一套与目标架构相符的基础骨架：

### 6.1 TCP Server 和连接管理

`src/MesControlAgv.Mes/Services/ShineLabTcpServer.cs` 已实现：

- 中控监听 TCP 端口；
- 接收 ShineLab Client 主动连接；
- 按换行读取 JSON；
- Certification 响应；
- 单一有效连接替换；
- 接收 UpdateInfo、AlarmInfo、SampleFinish、TaskFinish、TaskError、Result。

`ShineLabConnectionManager` 已实现：

- 中控向 ShineLab 发送 Config/Command；
- 自动生成 `strID`；
- 按 `strID` 等待命令响应；
- 连接失败时返回未知结果，避免自动盲目重试。

### 6.2 MES 任务和恢复

`ShineLabTaskRepository` 已实现：

- `task_uuid` 唯一约束；
- 相同任务重复创建返回原任务；
- 相同 `task_uuid` 携带不同内容时返回冲突；
- TaskCreated、Config、Command、状态、结果和异常事件记录；
- Config/Command 超时或连接失败进入 `Unknown`；
- MES 重启时未闭环任务恢复为 `Unknown`。

### 6.3 WPF 页面

当前 WPF 已有：

- ShineLab 设备状态查询页；
- 当前设备、任务、样品、通道、位置、阶段、进度和报警展示模型；
- 实验阶段的 Config/Command 任务下发页；
- 任务列表和任务事件查询接口。

## 7. 当前项目仍需适配的事项

### 7.1 JSON 命名策略风险

`ShineLabCommandService` 使用默认 `System.Text.Json` 序列化嵌套 `ShineLabSampleData`，可能生成：

```json
{
  "SampleId": "S-01",
  "SampleName": "标准样",
  "Position": 11,
  "Channel": "A"
}
```

而协议使用：

```json
{
  "sampleID": "S-01",
  "sampleName": "标准样",
  "position": 11,
  "channel": "A"
}
```

必须使用显式外部 DTO、`JsonPropertyName` 或统一命名策略，并增加序列化快照测试。不能依赖厂家是否大小写不敏感。

### 7.2 当前响应解析依赖 body.result

中控当前按 `body.result` 识别 Config/Command 响应。如果厂家按协议通用表把 `result/msg` 放在外层，中控将无法完成响应关联。因此必须先统一协议结构，或在适配层明确兼容规则。

### 7.3 当前状态缓存没有解析 values 测点

状态缓存主要读取扩展字段，如 task_uuid、sampleID、stage、progress、errorCode。协议原有 `values` 数组中的流量计、阀和测点告警尚未形成结构化模型。

### 7.4 当前 WPF TCP 任务页只发送单个样品

中控 API 的 `sampleData` 类型可以承载多个样品，但当前实验任务页每次只创建一行样品。要实现真正的序列进样，还需要批量任务界面、顺序校验、每个样品的结果和批次完成统计。

### 7.5 当前 CSV/RPA 路径不等于 TCP 自动运行

现有 CSV/RPA 路径已经验证过 ShineLab 可以接受 MES 生成的 CSV，但当前脚本明确不点击“运行”，只做导入和人工复核。因此不能把 CSV 导入成功视为 TCP 控制、自动进样或结果闭环成功。

### 7.6 当前实验工作流尚未真正驱动仪器

`docs/EXPERIMENT-WORKFLOW-ARCHITECTURE.md` 已明确：当前 `InstrumentOperation` 主要停留在 `Prepared`，不会实际执行设备 I/O。该协议即使补齐，也还需要通过仪器能力层接入统一工作流，不能直接把原始 `Command` 塞进流程节点。

### 7.7 仓库中存在旧方向 TCP Client 骨架

`src/MesControlAgv.ShineLabDispatcher/ShineLabTcpProtocol.cs` 中仍有“MES 作为 TCP Client、ShineLab 作为 Server”的旧注释和短连接调用方式。该路径与当前“ShineLab Client、中控 Server、长连接”方案不同，后续必须明确废弃、隔离或改名，防止现场误用。

## 8. 要求 ShineLab 厂家补充的 P0 清单

以下项目完成前，不建议进入真机自动运行：

## 9. 建议的联调验收顺序

### 第一阶段：连接和只读

- ShineLab 开机常驻并主动连接中控；
- 中控收到 Certification 并返回明确结果；
- 连续 10 分钟每秒收到 UpdateInfo；
- 中控能区分在线、空闲、运行、异常和离线；
- 断开 TCP 后 ShineLab 自动重连并重新 Certification；
- 中控不打开 SHA-18i/D160+ 串口。

### 第二阶段：单样品闭环

- 中控创建一条带完整方法和位置的样品任务；
- ShineLab 返回 Config Success；
- 中控发送启动命令；
- ShineLab 返回 Command Success；
- 中控收到 SampleFinish、Result、TaskFinish；
- `strID` 和 `task_uuid` 均能正确关联；
- 结果文件和检测数据均可归档。

### 第三阶段：异常和恢复

- 设备忙时拒绝第二个任务；
- 缺瓶、停止、清洗和设备异常均有明确上报；
- Command 超时后不自动重发；
- 重连后可通过 QueryTask 或状态上报确认任务真实结果；
- 相同 task_uuid 重复提交不会重复进样；
- MES 重启后未闭环任务进入 Unknown 并支持人工对账。

### 第四阶段：序列进样

- 一次下发多条样品；
- 样品顺序与中控一致；
- 每个样品均有独立完成和结果关联；
- 支持循环次数和方法差异；
- 中间样品失败时按约定继续或停止；
- 整批 TaskFinish 的数量统计正确；
- 重复提交整批任务不会重复进样。

## 10. 最终评审意见

本协议的优点是：通信角色和基本方法与当前中控架构兼容，能够支撑建立 ShineLab Client 到中控 Server 的基础通道。

本协议的主要问题是：它仍停留在通用报文示例层面，未完成 SHA-18i 专用化，也未定义可验证的任务状态机、序列语义、错误码、结果归档和断线恢复机制。

因此最终意见为：

> **架构方向通过；接口草案部分通过；业务闭环不通过；生产协议不通过。**

在厂家补充 P0 项目并通过连接、单样品、异常恢复和序列进样四阶段验收前，不得宣称已实现离子色谱仪器的自动化闭环。
