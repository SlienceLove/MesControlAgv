# AUBO Modbus 通讯角色与下一步实施计划

更新时间：2026-08-31  
范围：AUBO 控制器、当前“测试”工程、总控电脑 `192.168.1.11`、项目内
`AuboModbusBridge` 和 `res/modbus从站地址表_v1.15.xlsx`。

## 1. 结论先行

当前现场存在两种不同的通信方向，不能用同一个“Modbus 从站”概念混在一起：

| 场景 | 谁是 Modbus 主站 | 谁是 Modbus 从站/服务器 | 地址/寄存器 | 当前状态 |
|---|---|---|---|---|
| 当前“测试”工程 | AUBO Lua 工程 | 总控电脑 | `192.168.1.11:502`，Unit 1，保持寄存器 0/1 | 已在 AUBO 中注册 `总控输入/总控输出`，总控 502 尚无监听 |
| AUBO 官方从站表 | 总控 PLC/中控 | AUBO 控制器 | AUBO 从站地址表中的 300~555 等 | 尚未实现为中控 Modbus 主站，也未与当前工程确认一致 |
| 中控控制面 | 中控客户端 | AUBO RPC 服务 | WebSocket `192.168.1.102:9012` | 已现场验证；状态/加载/启动通过此链路完成 |

因此，对当前“测试”工程，**如果要让它访问总控寄存器，中控需要运行 Modbus
TCP Server**。但这不等于“中控现在已经具备完整的 Modbus 控制模块”：项目中
只有一个独立的最小 Server，还没有集成到 MES/WPF，也没有形成经过现场确认的
命令、应答和动作闭环。

## 1.1 中控未来不物理直连 AGV 时的推荐方式

物理直连不是协议前提。推荐的部署拓扑是：

```text
中控服务器/操作站
        │
        ▼
厂区控制交换机或无线 AP/Bridge
        │       （二层透明桥，或明确配置的三层路由）
        ▼
AGV 车载交换机/无线终端
        ├── AGV 控制器（192.168.1.2）
        └── AUBO（192.168.1.102）
```

这里的关键不是“中控是否直接插在 AGV 上”，而是中控在逻辑上能够稳定访问：

- AUBO `192.168.1.102:9012`（WebSocket JSON-RPC 控制面）；
- AGV `192.168.1.2` 的已批准状态/命令/控制权端口；
- 只有继续兼容旧“测试”工程时，才需要 AUBO → 中控
  `192.168.1.11:502`（Modbus 数据面）。

若使用三层路由而不是同一二层网段，必须由网络负责人配置静态路由和防火墙；
不能依赖 NAT 隐藏 AUBO 或 AGV 地址。移动 AGV 的无线链路还必须具备漫游/覆盖
和断线恢复策略，网络断线时任务结果必须进入 `unknown/manual_intervention_required`，
不得自动重发运动命令。

## 1.2 协议选择建议

最终建议采用“**JSON-RPC 控制面 + 明确的工程级回执**”：

1. 中控通过 AUBO WebSocket JSON-RPC `9012`完成状态读取、工程加载、启动/停止和
   后续受控接口；这条链路不要求中控与 AGV 之间存在一根物理直连网线。
2. 当前 `测试` 工程中的 `总控输入/总控输出` Modbus 信号只作为旧工程兼容层；
   中控若需要支持它，运行 `AuboModbusBridge` 作为 `.11:502` Server，但保持
   HR0=0，先验证连接，不把它当作最终动作控制 API。
3. `res/modbus从站地址表_v1.15.xlsx`对应的“中控 Master → AUBO Slave”方案只在
   项目明确要求 PLC 风格寄存器控制时单独实施。它需要新建 Modbus TCP Master、
   确认固件/Modbus 版本、工程序号和 399/400 写入语义，不能与旧工程主站方案并用。

换句话说：**未来非直连部署仍可以使用 JSON-RPC 直接访问 AUBO；是否运行中控
Modbus Server 取决于是否继续运行当前旧 Lua 工程，不取决于中控是否物理连接 AGV。**

## 2. 现场与代码证据

### 2.1 当前工程的 Modbus 方向

同名历史工程 `测试.lua` 中包含：

```lua
modbusAddSignal("192.168.1.11,502", 1, 0, 3, "总控输入", false)
modbusAddSignal("192.168.1.11,502", 1, 1, 3, "总控输出", false)
```

这表示 AUBO 控制器主动连接总控电脑的 `502` 端口，读取/更新远程保持寄存器。
AUBO 官方 Modbus 文档也采用“先 `modbusAddSignal`，再用
`modbusGetSignalStatus` 读取信号”的流程。[ARCS Modbus 使用指南](https://docs.aubo-robotics.cn/application_notes/29-arcs-modbus/)

本次现场 RPC 读取到：

- `总控输入`：索引 0、类型 3、值 0、原始错误码 `-1`；
- `总控输出`：索引 1、类型 3、值 0、原始错误码 `-1`；
- 总控电脑检查时 `192.168.1.11:502` 没有监听进程。

这说明信号对象已在 AUBO 内注册，但总控 Modbus 数据面尚未闭环。`-1` 的精确
含义仍应以当前固件错误枚举确认；结合 502 无监听，只能先按“未建立有效更新”
处理，不能把它当作正常通讯。

### 2.2 项目现有中控模块

`src/MesControlAgv.AuboModbusBridge` 已实现一个最小 Modbus TCP Server：

- 监听 `192.168.1.11:502`，Unit ID `1`；
- 支持功能码 `03`、`06`、`16`；
- 初始 HR0/HR1 为 0；
- HR0 非零写入默认拒绝，只有显式 `--allow-motion` 才允许；
- 通过控制台 `get/set` 查看或修改寄存器；
- 不提供 MES HTTP API、WPF 绑定、持久化审计或动作结果状态机。

所以它目前是“兼容历史 Lua 模板的独立验证服务器”，不是已经完成的生产级
Modbus 控制模块。默认启动时不带 `--allow-motion`，不会允许非零 HR0 命令。

### 2.3 `res/modbus从站地址表_v1.15.xlsx` 的含义

该表是 AUBO **作为 Modbus 从站**时的寄存器地址表，关键内容包括：

- 通用整数寄存器 `300~555` 对应控制器内部 `0~255`；
- `300~318` 一组为只读身份、模式、安全、停止状态等信息；
- `399` 为“切换工程”，备注要求使用示教器配置中的工程序号；
- `400` 为“控制工程”；
- `401` 为工程运行速度，取值 `0~100`；
- `202` 为工程运行状态，`203` 为心跳；
- 控制器接口板数字输入/输出等也有独立的地址段。

这套地址表用于“中控/PLC 作为 Modbus 主站访问 AUBO 从站 `192.168.1.102:502`”
的方案，和当前工程中“AUBO 主站访问中控 `192.168.1.11:502`”是反方向。
在没有确认现场固件是否启用 AUBO Modbus 从站、从站端口、Unit ID 和版本兼容性
之前，不得直接向 399/400 写入。

## 3. 推荐实施路线

### 阶段 0：固定通信角色，禁止混用

- 当前控制面继续使用已验证的 WebSocket JSON-RPC `9012`；
- 当前“测试”工程若需要总控寄存器，采用“中控 Server、AUBO Master”方向；
- 暂不实施“中控 Modbus Master、AUBO Slave”方向；
- 不把 AUBO 从站地址表中的 399/400 误当成当前工程的 HR0/HR1；
- 不启动第二个占用 502 的程序，不修改控制器端口、Unit ID 或工程配置。

### 阶段 1：先闭环只读 Modbus 数据面

目标是证明 AUBO 能从总控电脑读到 HR0/HR1，期间不触发动作：

1. 确认当前没有其他程序占用 `192.168.1.11:502`；
2. 构建并启动最小 Bridge，**不带** `--allow-motion`：

   ```powershell
   dotnet build .\src\MesControlAgv.AuboModbusBridge -c Release
   dotnet run --project .\src\MesControlAgv.AuboModbusBridge -- `
     --bind 192.168.1.11 --port 502
   ```

3. 另一个 PowerShell 验证端口：

   ```powershell
   Test-NetConnection 192.168.1.11 -Port 502 -InformationLevel Detailed
   ```

4. 通过已验证的 WebSocket RPC 只读重新读取 `总控输入/总控输出` 的值与错误码；
5. 预期 HR0/HR1 保持 0，且错误状态应由“未更新”变为当前固件定义的正常/已连接
   状态；
6. 若仍为错误，不写寄存器，检查 Windows 防火墙、AUBO 到 `.11` 的路由和
   `modbusAddSignal` 参数。

当前“测试.lua”可见代码主要注册 Modbus 信号，随后执行视觉 Socket、关节/直线
运动和弹窗；未看到用 HR0 读取动作编号的完整分支。因此阶段 1 只能证明通讯，
不能证明 HR0 能控制当前工程。

### 阶段 2：确认当前工程的真实数据契约

由厂家/项目方确认并记录：

- `总控输入` 是否真的被当前工程读取；
- `总控输出` 的含义、结果码和清零时机；
- HR0 是否为命令、是否需要上升沿/序列号；
- 哪些值允许写入，是否允许重复命令；
- 当前工程完成/失败是通过 Modbus、视觉 Socket、弹窗还是其他方式反馈；
- 视觉服务器实际地址/端口和超时策略。

未确认前，HR0 只保持 0，HR1 只读，不把 `1..5` 写入 Bridge。

### 阶段 3：将 Bridge 纳入中控，但保持分层

如果阶段 1/2 证明当前工程确实需要中控 Modbus Server，再做以下实现：

1. 将 Bridge 核心抽为可测试的 Modbus TCP Server/寄存器状态组件；
2. 增加固定的 HR0/HR1 数据契约、序列号、单次命令、超时和未知结果状态；
3. 由 MES 服务提供受控 API，禁止 WPF 直接任意写寄存器；
4. 写入前检查运行模式、工程身份、急停/安全状态和当前任务是否为空；
5. 所有写入记录操作 ID、寄存器、值、时间、响应和最终结果；
6. 默认只读，控制写入必须经过独立配置和现场双重确认；
7. 为 03/06/16、非法地址、重复命令、断线和重连增加自动化测试。

### 阶段 4：另行评估 AUBO 从站表方案

只有项目方明确选择“中控作为 Modbus Master 直接控制 AUBO”时，才新增独立的
Modbus TCP Client：

- 先读取 300~318、202、203、401 等只读/读写状态并记录版本；
- 确认当前控制器 Modbus 版本与 `v1.15` 表的兼容性；
- 由示教器确认工程序号，再设计 399/400 的写入流程；
- 任何写入都必须有安全门禁、幂等 ID、回读和未知结果处理；
- 该方案不能和当前 Lua 主站方案同时启用同一控制链路。

## 4. 当前建议的最小下一步

当前“测试”工程已经运行过一次且状态正常。建议不再重复启动，先做以下工作：

1. 保持工程当前状态，由现场人员确认是否仍停在 `trr` 弹窗；
2. 启动不带 `--allow-motion` 的 `AuboModbusBridge`；
3. 复核 AUBO Modbus 信号错误状态是否恢复；
4. 不写 HR0/HR1，不改变工程，不触发新的运动；
5. 将复核结果与当前工程的 Modbus/视觉契约交给厂家确认。

只有阶段 1/2 完成后，才决定是继续“中控 Server + AUBO Master”，还是改做
“中控 Master + AUBO Slave”。两种方案的寄存器地址、写入方向和安全控制完全不同。
