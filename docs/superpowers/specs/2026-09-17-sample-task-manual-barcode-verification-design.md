# 样品任务表人工条码核对设计

日期：2026-09-17

## 1. 目标

在中控平台中建立最小的样品条码核对门禁：实验任务运行前，操作员在中控页面查看任务批次、任务表样品条码和样品位，目视核对现场样品瓶标签；核对完成后，中控保存留痕并锁定本次核对的任务表版本，之后才允许上传任务和启动实验。

本设计不连接仪器 USB 扫码枪。仪器工作站与中控分别运行在不同电脑，仪器 USB 接口上的扫码枪输入不会直接进入中控 WPF。

## 2. 当前事实与边界

- 中控 WPF 最终运行在独立中控电脑。
- 工作站扫码枪连接在仪器工作站电脑的 USB 接口。
- 当前工作站 HTTP 接口没有提供“最后一次实际扫码结果”。
- 已验证的正式工作站节点只启动厂家已有任务，不创建任务、不上传任务表、不写轨迹。
- 厂家任务表上传格式和任务创建接口尚未交付；本设计只规定中控侧核对状态和未来上传准入条件，不猜测厂家字段或报文。
- 任务表导入只负责准备任务，不得隐式启动设备。

## 3. 方案选择

采用批次级人工核对：操作员在非弹窗页面完成目视检查，然后点击一次“核对完成”。不要求逐行点击确认，不新增中控扫码枪，也不要求厂家增加扫码结果接口。

暂不采用：

- 纯口头或线下核对：无法阻止未核对任务运行，也没有审计记录。
- 仪器扫码枪直连中控：两台电脑之间不能直接传递 USB 键盘输入。
- USB 网络共享或切换器：增加现场连接和稳定性问题。
- 中控专用扫码枪：作为未来增强保留，不属于当前阶段。

## 4. 核心数据

每个实验任务保存一份样品核对记录：

| 字段 | 含义 |
| --- | --- |
| `VerificationId` | 核对记录 ID |
| `ExperimentJobId` | 所属实验任务 |
| `Revision` | 任务表样品快照版本，从 1 递增 |
| `Status` | `Draft`、`ReadyForVerification`、`Verified`、`Invalidated` |
| `Rows` | 本版本需要核对的样品行快照 |
| `SnapshotHash` | 样品行身份、顺序、条码和位置的确定性摘要 |
| `VerifiedBy` | 核对操作人 |
| `VerifiedAt` | 核对时间 |
| `VerificationNote` | 可选现场备注 |
| `InvalidatedAt` | 失效时间 |
| `InvalidationReason` | 失效原因 |

每条样品行至少包含：

| 字段 | 含义 |
| --- | --- |
| `RowId` | 任务表内稳定行 ID |
| `SampleId` | 中控样品编号 |
| `SampleBarcode` | 现场瓶身应显示的条码 |
| `Position` | 样品位或托盘位置 |
| `DisplayName` | 页面显示名称，可为空 |

条码按去除首尾空格后的原值保存和比较；当前阶段不擅自改变大小写，也不解析厂商条码内部编码规则。

## 5. 状态规则

### 5.1 草稿和自动校验

任务表样品快照创建或更新后进入 `Draft`。中控自动校验：

- `SampleId`、`SampleBarcode` 和 `Position` 均不为空。
- 同一批次不存在重复 `RowId`。
- 同一批次不存在重复样品位。
- 同一条码不会绑定到两个不同样品。
- 条码已经存在于中控样品列表，并且对应样品属于当前批次。

全部通过后进入 `ReadyForVerification`；任何错误都保留在草稿状态，并在具体行显示原因。

### 5.2 人工核对

操作员打开任务详情中的“样品核对”区域，逐项查看：

- 样品编号。
- 预录条码。
- 样品位。
- 现场瓶身标签。

确认整批一致后，在页面点击“核对完成”。该按钮不是弹窗，只是页面上的明确业务动作。中控保存操作人、时间、样品行快照和摘要，状态转为 `Verified`。

### 5.3 失效和重新核对

已核对后发生以下任一变化，立即转为 `Invalidated`：

- 增加或删除样品行。
- 修改样品编号、条码、位置或顺序。
- 重新导入任务表并产生不同样品快照摘要。
- 任务改绑到其他批次。

失效后不得沿用旧核对记录。自动校验重新通过后，操作员需要再次点击“核对完成”。历史核对记录保留用于审计，不覆盖或删除。

## 6. WPF 页面

在实验任务详情或后续任务表准备页面增加“样品核对”区域，不新增弹窗。

页面至少展示：

- 批次号、实验任务号、任务表版本。
- 样品编号、条码、位置和逐行校验结果。
- 当前状态：待完善、待核对、已核对、已失效。
- 最近核对人、核对时间和失效原因。
- “核对完成”按钮。

交互规则：

- 只有自动校验通过时，“核对完成”可用。
- 已核对版本再次打开时只读展示，不重复确认。
- 修改任务表后立即显示“核对已失效”。
- 未核对或已失效时，任务上传和运行入口不可用，并直接显示阻止原因。
- 页面不自动读取仪器扫码枪，也不伪装实际扫码结果。

## 7. 上传与运行边界

未来厂家任务表上传能力接入后，上传服务必须接收 `ExperimentJobId + Revision + SnapshotHash`，并在发送厂家请求前重新读取当前核对记录：

1. 核对状态必须为 `Verified`。
2. 请求版本和摘要必须与当前记录一致。
3. 上传内容中的样品编号、条码、位置和顺序必须来自该快照。
4. 上传只创建或更新厂家任务，不启动实验。
5. 厂家明确接收后保存厂家任务号和响应证据。
6. 上传结果不明确时不自动重传，也不启动任务；操作员先查询厂家任务是否已经创建。
7. 正式运行只引用已确认接收的厂家任务号，并继续沿用现有单次启动和 Running 证据规则。

厂家格式交付后，只增加“厂家表格行 -> 中控样品行/任务参数”的映射，不改变本设计的人工核对和版本门禁。

## 8. 并发与审计

- 核对命令携带请求 ID，重复提交同一请求只返回原结果。
- 核对时使用当前 `Revision` 和 `SnapshotHash` 做并发检查；页面加载后若任务表被他人修改，本次核对失败并要求刷新。
- 每次核对和失效都写入实验任务审计，至少记录操作人、时间、版本、摘要和原因。
- 同一实验任务只有当前版本可以用于上传；历史版本保持只读。
- 已运行任务的核对快照永久保留，不能被后续任务表修改替换。

## 9. 错误处理

| 情况 | 行为 |
| --- | --- |
| 条码为空、重复或未登记 | 阻止核对，定位到具体行 |
| 样品不属于当前批次 | 阻止核对 |
| 样品位为空或重复 | 阻止核对 |
| 核对期间任务表被修改 | 返回版本冲突，要求刷新 |
| 核对后任务表改变 | 自动失效，禁止上传和运行 |
| 厂家上传明确失败 | 保持已核对状态，但标记上传失败；不启动 |
| 厂家上传结果未知 | 标记待核销，不自动重传、不启动 |
| 工作站启动结果未知 | 沿用现有 Unknown 规则，停止后续流程 |

人工目视核对仍存在人为误判风险。本阶段接受该限制，通过操作人、时间、版本锁定和审计减少无记录风险；不声称实现机器自动防错。

## 10. 自动化验证

至少覆盖：

- 完整且已登记的样品行可以进入待核对状态。
- 缺失、重复、跨批次条码和重复位置不能核对。
- 核对保存操作人、时间、版本和摘要。
- 重复请求幂等。
- 并发修改导致核对冲突。
- 任一核对字段变化使旧记录失效。
- 未核对和已失效状态禁止上传与运行。
- 上传使用已核对的同一版本和摘要。
- 上传操作不会启动设备。
- 厂家结果不明确时不自动重传。
- 旧实验任务继续读取，不强制补历史核对数据。

## 11. 验收标准

1. 操作员可以在中控页面查看某个实验任务的完整样品条码和位置列表。
2. 自动校验失败时能够定位具体问题行。
3. 操作员无需弹窗即可完成批次级“核对完成”。
4. 中控保存可审计的核对人、时间和任务表版本。
5. 核对后的任务表被修改时，旧核对立即失效。
6. 未核对、已失效或版本不一致时不能上传或运行。
7. 当前阶段不依赖仪器 USB 扫码枪或厂家扫码回传接口。
8. 后续厂家任务表格式接入时无需改变人工核对状态机。

## 12. 非目标

- 不从仪器 USB 接口读取扫码枪输入。
- 不实现 USB 网络共享、扫码枪切换器或远程桌面键盘转发。
- 不新增机器自动扫码或图像识别。
- 不猜测尚未交付的厂家任务表字段和上传协议。
- 不在导入任务表时隐式启动工作站。
- 不改变当前开盖分液节点的单次启动、Running 证据和 Unknown 处理。
- 不在本阶段实现耗材库存、采购、仓库或完整 LIMS 功能。
