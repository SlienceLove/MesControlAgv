# 离子色谱通讯模块切换记录 · 2026-09-11

## 当前模块边界

本次现场使用的核电 YLoop 模块仅用于通讯测试，不包含可执行的实际进样方法。
它的报文外壳可作为协议形态参考，但不能作为真实进样流程、Config 参数或
Command 动作的验收依据。该模块的业务通讯接口仍由厂商重新开发中。

当前结论：

- 已验证 TCP 建链、LF-JSON 识别、Certification 响应和状态保持；
- 现场帧的 `equipmentCode`、`strCode` 为空，`UpdateInfo.status=99`；
- 未验证真实进样、方法选择、Config/Command 或结果闭环；
- 不因 YLoop 通讯成功而放行任何实际进样动作。

## 下一目标：锐克模块

锐克模块具备实际进样能力。现场已确认其 `Command` 使用下方截图对应的严格
模板；TCP 传输仍沿用已验证的 LF-JSON。实际 `Config` 字段和结果上报闭环仍需
单独确认，不能因 `Command` 模板确认而直接放行批量进样。切换后按以下顺序处理：

1. 保持 MES 被动监听，仅记录连接建立、首包长度、方向、十六进制前缀/哈希和
   到包间隔，不发送 Certification、Config、Command 或设备动作。
2. 离线判断编码、分帧、粘包/半包、请求/响应方向，并保存脱敏原始帧。
3. 只有在帧边界和字段语义能够稳定重复解析后，才增加解析器和回放测试。
4. 先做只读身份/状态验证；实际进样前必须取得厂商的正式字段、响应和动作
   映射确认。

### 首次锐克连接证据

2026-09-11 首次点击连接时，服务端实际收到来自 `192.168.10.108:64105`
的 LF-JSON 流：

- 客户端发送两条 `Certification`，`equipmentCode` 和 `strCode` 均为空；
- MES 按收到的 LF-JSON 格式返回两次 `body.result=Success`；
- 随后客户端发送 `UpdateInfo`，可见状态先为 `99`，之后为 `0`；
- MES 没有异常、超时断开或主动踢连接；
- 该连接累计 82 次读取、约 8.9 KB 后由客户端主动关闭。

本次尚未收到 `Heart`、`BindModule`、Config/Command 或进样相关报文。
因此“点击后卡住”暂不能归因于 MES 踢连接，更可能是锐克客户端在认证成功后
仍等待厂商特定的设备标识或模块响应。未取得厂商确认前不补发猜测性报文。

本次证明端口配置问题已排除，但不等于真实进样协议已经验收。

### 只读稳定性观察

端口修正后的连接完成约 5 分钟只读观察：

## 锐克协议对照准入清单

### 已观察并与下游表一致

- TCP Client → 中控 TCP Server；目标端口为 `5500`；
- UTF-8 LF-JSON 分帧；
- 通用外壳包含 `strID`、`strMethod`、`equipmentCode`、`strCode`、`body`；
- 已观察到 `Certification` 和 `UpdateInfo`；
- 当前只读状态可稳定解析为 `STN61_01/status=0`。

### 发送 Config 前必须确认

- 锐克正式 `equipmentCode`、`strCode` 和认证响应的完整字段；
- `Config.body.sampleData` 中方法、位置、通道、体积、处理方法的准确字段；
- `Config` 响应是否携带 `task_uuid`，以及失败码和重复请求语义；
- `Command` 响应与结果闭环是否携带额外状态字段；
- `SampleFinish`、`TaskFinish`、`TaskError`、`Result` 的完整上报格式。

在上述 Config、结果上报和重复请求语义没有厂商样例或现场成功回报前，MES 只
保持监听和离线预览，不发送 Config；Command 仅在单条 Config 预检成功并取得
现场人员明确授权后发送。

## 厂商截图补充：Command 启动样例（现场已确认适用于锐克）

用户提供的协议截图展示了一个 `Ge` 设备的下发样例，结构为：

```json
{
  "strID": "08-osc-00099-W",
  "strMethod": "Command",
  "equipmentCode": "Ge",
  "body": {
    "chan": "A",
    "action": 0
  }
}
```

截图标注的动作含义为：

- `action: 0`：启动取样/进样；
- `action: 2`：停止取样；
- `action: 7`：清洗。

响应外壳为同一 `strID`、`strMethod`、`equipmentCode`，`body` 中回传
`chan`、`action`、`result`（`Success`/`Failed`）和 `msg`。

现场已确认该模板就是锐克模块使用的模板；截图中的 `Ge` 是示例设备编码，实际
外壳仍由当前连接的设备编码填充。MES 线上 `Command.body` 严格只发送 `chan`
和 `action`，不附带 `task_uuid`、样品号或方法等扩展字段。动作码记录为：

- `action: 0`：启动取样/进样；
- `action: 2`：停止取样；
- `action: 7`：清洗。

`TaskUuid` 和样品信息仅保留在 MES 本地任务与审计记录中，用于响应关联和追溯。
Config 参数及 `SampleFinish`、`TaskFinish`、`TaskError`、`Result` 上报格式仍
需厂商/现场进一步确认。

### 空位 action=0 试发与 Ge 身份复核

在现场确认允许空位运行后，MES 于 2026-09-11 试发了一条 `chan=A`、`action=0`
的严格 Command。请求使用本地关联号
`rike-empty-20260911-092201826`，线上 body 未携带该字段。10 秒内未收到锐克
可关联的响应，HTTP 接口返回 `503 Service Unavailable`；TCP 连接仍保持，设备
状态持续为 `Idle`、`hasActiveTask=false`，没有观察到运行或进样状态。该结果只
能判定为“下发结果未知”，不能视为设备返回失败，也没有自动重试。

随后按原始示例设备编码 `Ge` 进行了路由复核，请求号为
`rike-ge-empty-20260911-try01`。由于当前连接握手上报的设备编码是
`STN61_01`，MES 的设备隔离逻辑在本地直接返回 `503`（设备 `Ge` 未连接），未
向 TCP 连接写入任何字节。不能用 `Ge` 覆盖当前设备身份；如需验证该编码，必须
由锐克客户端实际上报 `Ge` 或取得厂商确认后再配置。

## 暂停条件

出现以下任一情况时，只保存证据并暂停，不猜测协议、不下发控制报文：

- 首包不是已支持格式，且无法从多次捕获中确定稳定边界；
- 只能看到半包或无方向依据，无法证明请求与响应的对应关系；
- 字段/状态/结果闭环含义不完整，尤其是进样位置、方法、体积和完成/失败上报；
- 厂商模块仍在开发，现场版本与提供的协议样例不一致。

## 通过条件

锐克模块必须先完成：通讯稳定、身份/状态可重复解析、只读回放通过、厂商
确认 Config/Command 和结果上报格式。之后才安排单条进样预检，再决定是否恢复
批量任务联调。
