# 可视化流程画布技术评估

> 评估日期：2026-08-19
> 当前项目依赖：`Nodify 7.3.0`，目标框架：`.NET 8 WPF`
> 结论类型：技术选型门禁，不代表已经开始 UI 重构

## 1. 结论先行

Nodify **可以承担本项目的流程画布渲染和基础交互层，但不能单独全面支撑实验流程编辑器**。

当前选型状态是：**允许作为 Spike 的候选画布内核，尚未批准进入正式 UI 实现**。静态 API、现有原型和依赖关系已经核对完成；连接约束、编辑历史、复制粘贴、复杂布局、运行态覆盖和大图性能仍须通过第 6 节的动态 Spike 验证。这里的“通过”只表示它足以承担 WPF 画布层，不表示 Nodify 会提供流程引擎或设备编排能力。

当前建议：

1. 暂不立即更换框架。
2. 保留 Nodify 作为可替换的 `Canvas Adapter`，不让领域模型依赖 Nodify 类型。
3. 先完成一个有量化验收标准的画布 Spike。
4. 如果 Spike 证明撤销/重做、复制粘贴、分组语义、大图性能或维护成本不达标，再切换到功能更完整的 Diagram 控件。

原因是：换框架只能解决一部分画布交互问题，不能替代我们仍然需要自己设计的流程版本、节点能力、边语义、运行状态、设备安全、资源占用和审计模型。Nodify 的优势是已经适配当前 WPF、项目已有可运行原型、MIT 许可且基础交互完整；它的缺点是业务编辑能力需要我们自行实现。

## 2. 评估依据

本评估基于：

- 当前 `src/MesControlAgv.Wpf/MesControlAgv.Wpf.csproj` 的 `Nodify 7.3.0` 引用。
- 本地 `Nodify.dll` 和 `Nodify.xml` 的公开 API。
- `ExperimentFlowEditorView.xaml` 的实际用法。
- `ExperimentFlowEditorViewModel.cs` 的连接、导入导出、颜色和自动布局代码。
- 目标实验流程架构和界面规划。

历史开发记录中的 `Nodify 2.2.0` 和 `Nodify.Compatibility` 已经过时，不能作为当前依赖依据。当前工程实际只直接引用 `Nodify 7.3.0`。

当前原型已经验证了：

```text
NodifyEditor.ItemsSource
NodifyEditor.Connections
PendingConnection
Connector
ConnectionTemplate
ItemTemplate
节点拖动、端口连线、连接标签、自定义节点模板
```

但原型中的以下能力都是业务代码自行实现的：

```text
ExperimentFlowConfigDto 导入/导出
分支颜色分配
简单层次化自动布局
连接来源/目标编辑
节点类型和业务描述
```

这说明 Nodify 当前是图形交互基础设施，不是流程领域模型或流程引擎。

## 3. 能力矩阵

### 3.1 Nodify 可以直接提供或较容易定制的能力

| 需求 | 判断 | 说明 |
| --- | --- | --- |
| 自定义节点外观 | 支持 | `ItemTemplate`、`Node`、`StateNode`、自定义容器模板 |
| 多输入/多输出端口 | 支持 | `Node.Input`、`Node.Output` 和 `Connector` |
| 拖拽创建连接 | 支持 | `PendingConnection`、开始/完成命令 |
| 自定义连接线 | 支持 | `ConnectionTemplate`、`BaseConnection`、文字、箭头、动画和方向 |
| 连接选中/删除/切断 | 支持 | 连接容器、Disconnect/Split/Cutting 相关 API |
| 节点拖动和框选 | 支持 | 多选、拖动、键盘导航、自动边缘平移 |
| 缩放和平移 | 支持 | `ViewportZoom`、`ViewportLocation`、内置手势 |
| 适应画布/定位节点 | 支持 | `FitToScreen`、`BringIntoView` |
| 网格吸附和对齐 | 支持 | `GridCellSize`、`AlignSelection` |
| 小地图 | 支持 | 独立 `Minimap` 控件 |
| 画布分组外观 | 支持 | `GroupingNode` 可移动、缩放和选择组内节点 |
| 只读运行态画布 | 支持 | 禁用拖动/连线并通过模板绑定运行状态 |
| 连接状态视觉覆盖 | 支持 | 自定义连接模板和数据绑定即可实现 |
| 中等规模图形渲染优化 | 部分支持 | 有 rendering optimizations，但不是完整的业务级虚拟化方案 |

### 3.2 需要我们自行实现的能力

| 需求 | Nodify 状态 | 需要建设的部分 |
| --- | --- | --- |
| 端口方向和连接约束 | 未提供业务约束 | `CanConnect` 校验服务、端口类型和基数规则 |
| 成功/失败/超时/条件边 | 只能画线和显示文字 | 共享边模型、边类型、条件 schema 和校验器 |
| 条件表达式编辑器 | 未提供 | 结构化条件构建器和安全求值器 |
| 节点类型目录 | 未提供 | 能力目录、配置 schema、版本和 Profile 检查 |
| 属性面板 | 仅提供模板承载 | 按节点 schema 生成 WPF 编辑器控件 |
| 领域序列化 | 未提供 | WorkflowDefinition/Version JSON 契约和迁移器 |
| 自动布局 | 未提供业务布局算法 | DAG/分支/泳道/分组布局服务 |
| 撤销/重做 | 未提供命令历史 | 编辑命令、快照或增量变更日志 |
| 复制/粘贴 | 未提供业务剪贴板 | 复制节点子图、重写 ID、处理边和资源引用 |
| 子流程/嵌套图 | 分组不是子流程 | 子流程引用、边界端口和导航模型 |
| 运行态节点执行 | 未提供 | 从 MES Run/NodeExecution 投影状态 |
| 校验问题定位 | 未提供领域关联 | NodeId/EdgeId 到画布容器和视口定位 |
| 版本比较 | 未提供 | 定义差异模型和可视化差异层 |
| 资源/设备占用提示 | 未提供 | 能力目录、资源状态和排程服务 |
| 权限/安全门禁 | 未提供 | 服务端授权和 UI 状态投影 |

### 3.3 不应由画布框架负责的能力

以下能力无论选择哪个画布库，都应留在 Domain/Application/MES/Adapter：

- 流程版本不可变和运行实例快照。
- AGV、机械臂、离子色谱仪的设备协议和状态对账。
- 资源租约、排程优先级和任务池。
- 设备写入安全策略、未知结果和人工恢复。
- 审计、权限和运行准入。
- 条件求值的数据来源和运行时状态机。

## 4. 关键发现

### 4.1 “Ready for undo/redo”不等于内建撤销重做

Nodify README 的功能说明使用了 “Ready for undo/redo”。当前 `Nodify.xml` 的 `EditorCommands` 包含缩放、选择、定位、适应画布、对齐和锁定等命令，但没有 Undo、Redo 或 History 命令。撤销/重做必须由应用层记录节点、边、参数和布局变更。

这不是阻断项，但必须把它当作一个独立的编辑基础设施，而不是以后顺手补一个按钮。

### 4.2 GroupingNode 不是子流程

`GroupingNode` 能提供带标题的可调整视觉分组，并支持组内选择和移动。它没有实验流程所需的：

- 子流程版本引用。
- 组边界输入/输出端口。
- 进入/退出子流程的运行语义。
- 独立的校验、资源和错误传播规则。

如果将来需要子流程，必须在领域模型中实现，画布只负责显示其外观。

### 4.3 连接约束不是框架语义

公开 API 提供连接拖拽、预览、吸附和断开，但没有面向业务的“输入端最多一个连接”“输出端必须有默认分支”“只能从设备输出连到条件输入”等规则。连接完成后必须由我们自己的 `WorkflowConnectionPolicy` 拒绝非法连接，并为 UI 提供原因。

### 4.4 自动布局需要自建

Nodify 提供对齐、适应画布、网格吸附和位置操作，但没有实验流程的 DAG、条件分支、并行汇合、泳道或嵌套分组布局算法。当前原型中的简单层次化布局不能覆盖复杂实验流程，应把布局算法封装成独立服务，避免写进 ViewModel。

### 4.5 性能优化不是完整虚拟化承诺

Nodify 公开了渲染和拖动优化开关，并说明面向数百节点优化；这对中等规模流程有利。但实验流程画布还会有自定义节点内容、连接标签、状态装饰、问题标记和运行数据，这些可能抵消优化效果。必须用真实节点模板做基准测试，不能仅凭 API 名称判断大图性能。

## 5. 画布适配层约束

为了保留切换框架的可能性，领域和应用层不得引用 Nodify 类型。建议定义内部适配边界：

```text
WorkflowDefinition / WorkflowEdgeDefinition
        |
        v
WorkflowDesignerViewModel
        |
        v
IWorkflowCanvasSurface (WPF-facing)
        |
        +-- NodifyCanvasAdapter (current)
        +-- CommercialDiagramAdapter (future option)
```

适配层负责：

- 节点和边的显示投影。
- 画布位置、缩放、平移和选中同步。
- 端口拖拽事件转为领域编辑命令。
- 视口定位和校验问题高亮。
- 只读/编辑/运行回放三种显示模式。

适配层不负责：

- 直接修改 MES 版本。
- 判断设备能力是否可执行。
- 求值条件。
- 发送设备命令。
- 决定重试或补偿。

## 6. Spike 验收方案

在决定是否换框架前，使用当前 Nodify 版本实现一个隔离的画布 Spike。Spike 不连接真实设备和 MES 写接口，只使用共享流程模型的内存样例。

### 6.1 数据集

至少准备三组定义：

| 数据集 | 规模和内容 |
| --- | --- |
| 线性实验 | 20 个节点、19 条边，包含 AGV、机械臂、仪器读取和定时等待 |
| 分支实验 | 60 个节点、90 条边，包含成功/失败/超时/条件边和人工确认 |
| 大图压力 | 200 个节点、350 条边，包含自定义节点、连接标签和状态装饰；另做 500 节点探索性测试 |

### 6.2 必测交互

1. 拖入节点、移动、框选、多选、对齐和网格吸附。
2. 从有方向端口创建非法和合法连接，非法连接必须即时给出原因。
3. 创建、编辑和删除带语义的边。
4. 复制一个包含 5 个节点和 6 条边的子图，确保所有 ID、端口和边引用正确重写。
5. 连续执行 100 次编辑操作后撤销，再重做，定义 JSON 必须逐字节或规范化等价恢复。
6. 自动布局后手动调整，再保存和重新加载，位置和边语义不能丢失。
7. 点击校验问题，画布定位并高亮对应节点或边。
8. 切换编辑、只读运行回放和禁用状态，不允许状态刷新改变布局。
9. 显示节点执行状态、边选择结果和实时数据摘要，不遮挡端口或连接标签。
10. 在大图中缩放、平移和拖动选区，记录加载时间、操作延迟和 UI 线程阻塞。

### 6.3 建议通过门槛

以下是进入正式 UI 开发的最低门槛：

- 线性和分支数据集加载、保存、重新加载无信息丢失。
- 100 次撤销/重做往返后节点、边、参数和位置保持一致。
- 合法/非法连接规则均由应用层测试覆盖，画布不会绕过规则。
- 200 节点/350 边数据集在开发机上加载时间不超过 2 秒，常见拖动、缩放和平移无明显卡顿；具体帧率和内存结果必须记录。
- 运行状态叠加不会改变定义 JSON，也不会触发设备调用。
- Spike 的 Nodify 适配代码不泄漏到 Contracts、Domain、MES 或设备工程。

### 6.4 判定结果

| 结果 | 后续动作 |
| --- | --- |
| 全部通过 | 继续使用 Nodify，进入统一模型和类型化属性开发 |
| 只有撤销/重做、剪贴板、布局缺失 | 仍可使用 Nodify，补齐应用层编辑服务 |
| 画布性能或自定义状态层无法满足 | 评估商业 Diagram 控件，保留领域模型和适配接口 |
| 需要完整 BPMN、子流程、泳道、审阅和版本差异且希望开箱即用 | 优先评估商业控件，不继续堆叠 Nodify 自研功能 |

## 7. 候选替代方案

| 方案 | 适配情况 | 优点 | 代价/风险 |
| --- | --- | --- | --- |
| Nodify 7.3.0 | 当前基线 | 已接入 WPF，MIT，基础交互和模板能力好 | 业务编辑服务全部自建 |
| Syncfusion WPF Diagram | 首选商业评估对象 | 通常覆盖撤销/重做、分组、序列化、自动布局等完整图形编辑能力 | 许可、主题迁移、API 迁移和供应商依赖 |
| DevExpress/Telerik/MindFusion/yFiles WPF | 商业备选 | 功能成熟、支持复杂图形和企业级交互 | 成本、许可和现有 WPF 风格适配 |
| GraphX | 不建议作为直接替换 | 图算法和图形可视化能力 | 不是完整流程编辑器，仍需大量自研 |
| NodeNetwork 等开源 WPF 节点控件 | 需单独验证 | MVVM 方向接近 | 社区/版本/高级交互能力需核实，未必比 Nodify 更完整 |
| React Flow/Rete.js 等 Web 方案 | 只有明确跨平台需求时考虑 | Web 生态和插件丰富 | 需要 WebView/前端栈，WPF 集成和部署复杂 |

不要因为 Nodify 缺少业务功能就直接切换到另一个同样需要自研业务层的开源控件。切换的理由必须是画布基础能力或维护成本不达标。

## 8. 最终建议

当前阶段采用以下决策：

```text
保留 Nodify 7.3.0 作为候选画布内核
            |
            v
先实现 Canvas Adapter + Spike
            |
            +-- 通过 -> 继续 Nodify
            |
            +-- 不通过 -> 评估商业 Diagram 控件
```

在 Spike 完成前：

- 不在 Nodify ViewModel 中继续增加设备业务逻辑。
- 不把 `ExperimentFlowNode`/`ExperimentFlowConnection` 当成最终领域模型。
- 不承诺 Nodify 已支持撤销重做、子流程、完整自动布局或无限大图。
- 不开始大规模 UI 视觉改造。

相关界面文档中的“使用 Nodify”均应理解为当前候选实现，而不是不可逆的架构承诺。
